# 请求签名（quote-token）

moomoo 网页端行情接口不依赖登录态鉴权，而是要求请求头 `quote-token` 携带一个由查询参数
计算出的签名。签名不对时服务端返回 `code = -403`，从参数上看不出任何问题，因此这篇文档
把签名规则单独说明。

本文适用于 `/quote-api/quote-v2/*` 下的接口；各接口的参数不同，但签名算法一致。

## 一、签名覆盖的范围

| 项 | 是否参与签名 |
| --- | --- |
| 查询参数（名称与值） | 参与，且顺序敏感 |
| 请求头 | 不参与 |
| 路径 | 不参与 |
| 请求体 | 不参与（本组接口为 `GET`，无请求体） |

只有查询参数参与签名，但参数的**书写顺序**、**值的形式**都会影响结果：同一组参数只要
换了顺序或把某个值从字符串写成数字，token 就会变。

## 二、签名输入的构造

把全部查询参数按请求中出现的顺序拼成一段紧凑 JSON：

- 键序与请求中的参数顺序一致，不排序；
- 所有值都先字符串化再写入，即值总是带引号；
- 不插入任何空格或换行；
- 只做最小转义：`"` → `\"`、`\` → `\\`、换行 → `\n`、回车 → `\r`、制表符 → `\t`；
  非 ASCII 字符按原始 UTF-8 保留，不转成 `\uXXXX`。

以 K 线接口的一组参数为例，请求中的顺序是 `stockId`、`marketType`、`type`、
`marketCode`、`instrumentType`、`subInstrumentType`、`_`，签名输入为：

```json
{"stockId":"70000294","marketType":"2","type":"2","marketCode":"70","instrumentType":"9","subInstrumentType":"9008","_":"1780507278122"}
```

不能直接用一个会按键名排序的 JSON 序列化器来生成这段文本，否则键序被改，token 必然不对。

## 三、计算步骤

1. **第一段摘要**：以字面量 `quote_web` 为密钥，对签名输入做 HMAC-SHA512，取十六进制
   结果的前 10 个字符。
2. **第二段摘要**：对上一步得到的 10 个字符做 SHA-256，取十六进制结果的前 10 个字符，
   即为 `quote-token`。
3. **空输入的降级**：签名输入为空字符串时，用字面量 `quote` 代替，再走上面两步。

伪代码：

```text
input  = "{...}"                                  // 为空时取 "quote"
step1  = hex(HMAC-SHA512("quote_web", input))[0:10]
token  = hex(SHA-256(step1))[0:10]
```

以签名输入 `{"a":"1","b":"2"}` 为例，中间结果为：

```text
step1 = 7e6164a879
token = 39adef0837
```

`quote_web` 取自网页前端产物，不是用户凭据，也不代表登录状态。

## 四、查询串的拼接

请求地址上的查询串必须与参与签名的参数顺序一致：

```text
stockId=70000294&marketType=2&type=2&marketCode=70&instrumentType=9&subInstrumentType=9008&_=1780507278122
```

- 键与值都要做 URL 转义（空格转成 `+`，`&`、`=`、`/` 等转义为百分号形式，中文按 UTF-8
  百分号编码）；
- 不能使用会按键名排序的编码方式，否则查询串顺序与签名顺序不一致。虽然服务端按收到的
  查询串顺序重算签名，但一旦顺序变化，token 就得跟着变，容易产生难以排查的错位。

## 五、校验向量

下面几组固定输入可用于校验实现是否正确，改动签名逻辑后必须仍然成立：

| 签名输入 | 说明 | quote-token |
| --- | --- | --- |
| （空字符串） | 空输入降级为 `quote` | `58af97268c` |
| `quote` | 与空输入等价 | `58af97268c` |
| `{"a":"1","b":"2"}` | 普通 JSON 输入 | `39adef0837` |
| `{"stockId":"70000294","marketType":"2","type":"2","marketCode":"70","instrumentType":"9","subInstrumentType":"9008","_":"1780507278122"}` | K 线接口完整参数 | `45671b44c1` |
| 同上，`_` 改为 `1780600000000` | 仅时间戳不同 | `7feb1b1665` |
| `{"stock_id":"76033806042898","market_type":"1","type":"0","subType":"0","_":"1781592384789"}` | 使用下划线命名的参数 | `055b0960ec` |

## 六、自检步骤

签名不通过时按顺序排查：

1. 打印签名输入，确认键序与请求中的参数顺序完全一致，且没有多余的空格；
2. 确认每个值都是字符串形式（`"2"` 而不是 `2`），空值也要保留为 `""`；
3. 确认参与签名的参数集合与实际发送的参数集合完全相同，没有遗漏或多发；
4. 用第五节的向量对照 `Sign("quote")` 是否为 `58af97268c`，先排除算法实现本身的问题；
5. 确认查询串与签名使用的是同一份参数列表，没有一处经过排序或重新拼装。

## 七、常见错误

| 现象 | 常见原因 |
| --- | --- |
| `code = -403`，参数看起来完全正确 | 签名输入的键序被排序，或拼接时用了 map |
| 只有部分参数变化时才对不上 | 数值被写成 JSON 数字而非字符串 |
| 时间戳很快变化后失败 | `_` 参数在签名与实际发送时取了两次不同的时间 |
| 中文或特殊字符参数失败 | JSON 转义方式不一致，或查询串未按 UTF-8 百分号编码 |
| 空参数请求失败 | 没有实现空输入降级为 `quote` |
