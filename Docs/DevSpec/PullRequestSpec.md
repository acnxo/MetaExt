# 递交与合并规范

本规范约定改动如何递交（分支、目标分支、PR）与如何合并。它约束的是**代理**的行为：
哪些决定可以自己作，哪些必须等 ACANX 明确指示。目的很直接——避免代理以「更快生效」
「文件需要」这类理由自行改变递交路径。

提交信息本身的写法见 [`CommitMessageSpec.md`](CommitMessageSpec.md)；版本与发版流程
另行约定。

## 一、总则

- 所有改动通过 PR 递交，**不直接推送到 `main` 或 `dev`**；
- 代理负责：拉分支、提交、推送、创建 PR；
- ACANX 负责：决定目标分支、审批、合并；
- 目标分支由本规范决定，**代理不得临时判断**；
- 拿不准时停下来问，不要先做了再解释。

## 二、目标分支

| 场景 | 目标分支 |
| --- | --- |
| 日常功能、缺陷修复、文档、CI 调整 | **`dev`** |
| `dev` 验收后发布到 `main` | `main`（发布 PR，由 ACANX 发起或明确指示） |

约束：

- 默认目标分支是 `dev`，这是常态，不需要每次确认；
- **指向 `main` 的 PR 必须由 ACANX 明确要求**，代理不得自行决定；
- 以下理由都不成立，不能作为改投 `main` 的依据：
  - 「工作流/配置文件只有进 `main` 才生效」；
  - 「走 `dev` 会多一轮，更慢」；
  - 「`main` 上正缺这个修复」；
  - 「之前也有 PR 直接进过 `main`」。
- 上述情况正确的做法是：仍然递交 `dev`，并在 PR 描述里说明「需要一次 `dev → main`
  才能生效」，由 ACANX 决定何时发布。

## 三、递交步骤

1. 从 `dev` 拉出分支（**不是从 `main`**，除非 ACANX 明确要求）；
2. 按 [`CommitMessageSpec.md`](CommitMessageSpec.md) 书写提交信息；
3. 推送分支，创建 PR 指向 `dev`；
4. PR 描述写清：改了什么、为什么改、怎么验证、有什么风险；
5. 等待 ACANX 审阅，**不合并**。

分支命名：

| 类型 | 前缀 | 示例 |
| --- | --- | --- |
| 新功能 | `feat/` | `feat/cna-trade-calendar` |
| 缺陷修复 | `fix/` | `fix/autotag-committer-identity` |
| 文档 | `docs/` | `docs/pull-request-spec` |
| CI/构建 | `ci/` | `ci/auto-tag-on-release` |
| 杂项 | `chore/` | `chore/release-process` |

## 四、禁止行为

代理不得执行以下操作，除非 ACANX 逐项明确授权：

- 把 PR 指向 `main`（发布 PR 除外，且需 ACANX 提出）；
- 合并任何 PR，包括自己创建的；
- 关闭他人创建的 PR；
- `git push --force` 或 `--force-with-lease`；
- 在未获授权时推送任何分支或标签；
- 改写已推送的历史（`rebase`、`amend`、`reset` 后强推）。

## 五、发布 PR

发布由 `dev` 指向 `main`，流程：

1. `dev` 上的改动经 `CICD` 验证并合并完毕；
2. 确认根目录 `VERSION` 已改为待发布版本（不带 `v` 前缀）；
3. 由 ACANX 发起或指示创建 `dev → main` 的发布 PR，标题形如 `Release:V0.1.1`；
4. 合并后 `AutoTag` 读取 `VERSION` 自动打标签并创建 Release；
5. 发布失败时不要删远端标签，修复后发新的补丁版本或手动补打。

## 六、检查清单

递交前逐项确认：

- [ ] 分支从 `dev` 拉出，不是从 `main`
- [ ] 提交信息符合 `CommitMessageSpec.md`
- [ ] PR 目标分支是 `dev`，除非 ACANX 明确要求指向 `main`
- [ ] PR 描述含变更说明、验证方式与影响面
- [ ] 没有夹带无关改动
- [ ] 没有自行合并、没有 force push
- [ ] 需要 `main` 才能生效的改动，已在 PR 描述中说明并等待指示

## 七、违规后的处理

发现代理违反了本规范时：

1. 立即关闭方向错误的 PR，不要试图用后续提交掩盖；
2. 基于正确分支重做，保留原提交信息；
3. 在回复中说明违反了哪一条、为什么、如何纠正；
4. 不擅自 force push 修正，除非 ACANX 明确同意。
