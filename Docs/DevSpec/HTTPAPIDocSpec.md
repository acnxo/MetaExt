# HTTP 接口实现规范

本规范约定本项目编写「外部 HTTP 接口封装」时的目录、命名、请求/响应处理、错误分类、
测试与文档要求。目标是让每个接口实现长得一样，调用方一眼能看出调用的是哪个接口，
排查问题时能快速定位是签名、参数、协议还是业务层面的问题。

现有实现：`component/quote/moomoo/quoteapiv2`，可对照阅读。

## 一、目录与文件组织

按「品类 → 渠道 → 接口组」分层；若一个外部服务有多个互不相关的接口，可放在 `sdk/<服务名>/`
下：

```
component/<品类>/<渠道>/<接口组>/
├── client.go     客户端、配置、请求装配、响应解析
├── signature.go  签名/鉴权等与请求签名相关的纯计算（该接口不需要签名时省略）
├── client_test.go
└── signature_test.go
```

- 一个接口组的公共部分（`Config`、`Client`、错误类型）放在 `client.go`；
- 签名、加密等可独立测试的计算放独立文件，`client.go` 只保留调用；
- 包注释写在主文件 `client.go` 上，说明本包职责、必须遵守的协议约束与命名约定。

## 二、命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 方法名 | 取接口路径末段的驼峰形式 | `/quote-api/quote-v2/get-kline` → `GetKLine` |
| 请求类型 | 方法名 + `Request` | `GetKLineRequest` |
| 返回元素类型 | 接口语义 + 元素名 | `KLineBar` |
| 配置/客户端 | 固定为 `Config` / `Client`，构造函数 `New` | `New(Config{})` |
| 私有 DTO | 小写，与接口字段对应 | `klinePayload`、`klineItem` |
| 大写下划线常量 | 默认值用 `Default` 前缀 | `DefaultBaseURL`、`DefaultTimeout` |

要求：

- 方法名必须能从路径推出来，禁止使用 `Fetch`、`Query`、`Kline` 这类看不出接口的泛化名；
- 同一个客户端有多个接口时，各接口的请求类型与返回类型都带自己的前缀，避免共用泛化类型；
- 方法名与接口路径的映射关系写进包注释，新增接口沿用同一规则。

## 三、客户端结构

```go
// Config 零值代表协议默认值，可按需覆盖。
type Config struct {
    BaseURL    string           // 站点，默认值见 DefaultBaseURL
    Path       string           // 接口路径，默认值见 DefaultXxxPath
    Timeout    time.Duration    // 单次请求超时
    HTTPClient *http.Client     // 可注入，测试与代理场景使用
    Now        func() time.Time // 可注入时钟，便于断言时间戳与签名
    // 接口特有的字段（如 CSRF、Locale）按需追加，同样以零值为默认。
}

func New(cfg Config) *Client
func (c *Client) Config() Config // 返回补齐默认值后的生效配置
```

- 零值配置必须可用：`withDefaults()` 补齐站点、路径、超时、时钟，并规整 URL 与路径格式
  （去掉 `BaseURL` 结尾斜杠、补 `Path` 前导斜杠）；
- 所有可注入依赖（HTTP 客户端、时钟）都必须有默认值，测试时用替换而不是全局变量；
- `Client` 创建后不保存可变状态，保证并发安全。

## 四、请求构造

- 查询参数用有序切片承载（`Param` / `Params`），**禁止**使用 `map` 或 `url.Values`：
  它们会重排键序，破坏依赖键序的签名；
- 参数值一律先字符串化为 `string` 再参与签名与拼接；
- 可空业务字段用「为空则取默认值」的写法，并在注释中说明默认取什么；
- 需要对调用方输入做最小校验（如必填字段为空时直接返回错误，不发请求）。

## 五、签名

- 签名实现放独立文件，导出的计算函数（`Sign`、`SignInput`、`SignParams`、`SignedQuery`）
  必须可以在没有网络的情况下单独测试；
- 签名输入需要保序时，手工拼字符串，不使用 `encoding/json`：标准库会按字典序输出键，
  转义方式也不一定与协议一致；
- 查询串按参数原顺序拼接，不能用会排序的编码方式；
- 签名常量（密钥、截断长度）集中定义，并注明来源（例如取自网页前端产物，不是用户凭据）；
- 在文件头部用注释说明签名对哪些因素敏感，避免后续维护者「顺手优化」导致签名失效。

## 六、响应解析

- 外层统一先解析 `code` / `message` / `data`，`code` 非成功值即视为失败，不做兜底；
- 对外暴露的结构体保留原值语义：
  - 价格、金额这类对精度敏感的字段用 `string` 承载，不在解析阶段转浮点；
  - 可能为 `null` 的字段用指针，区分「缺失」与「零值」；
- 接口字段类型混用（同字段有时是字符串、有时是数字）时，定义 `flexNum` 这类类型实现
  `json.UnmarshalJSON` 兼容多种写法，并让非法值回落到明确的默认值；
- 响应体读取要设上限（如 `io.LimitReader`，64MB），避免异常响应把内存打满。

## 七、错误处理

统一定义 `APIError`，至少包含：

| 字段 | 用途 |
| --- | --- |
| `Path` | 接口路径，区分同一客户端下的不同接口 |
| `URL` | 完整请求地址（含查询串），排查签名与参数问题 |
| `HTTPStatus` | HTTP 状态码，请求未到达服务端时为 0 |
| `Code` | 业务错误码，HTTP 层失败时为 0 |
| `Message` | 服务端错误描述或本地错误原因 |
| `Body` | 服务端响应体（截断），定位解析失败原因 |

约定：

- `Error()` 必须按「业务码 → HTTP 状态 → 原因」的优先级输出，且不能丢弃 `Message`，
  否则解析失败时调用方只看到「请求失败」，无从排查；
- 为高频判断提供语义化辅助函数（如判断签名被拒的 `IsTokenRejected`），调用方不直接比较魔法数字；
- 错误信息用中文，包含可定位的上下文（接口名、状态码、业务码）；
- 不把原始响应体整段塞进错误信息，超过阈值的内容要截断。

## 八、测试

每个接口至少覆盖：

1. **签名向量**：固定输入 → 固定 token，形成回归基线；包含空输入降级等边界；
2. **键序保真**：调换参数顺序后 token 必须不同，查询串不被重排；
3. **请求装配**：用 `httptest` 起本地服务端，断言路径、参数键序与取值、请求头、
   时间戳（注入固定时钟）；
4. **响应解析**：正常数据、`null` 字段、字符串/数值混用；
5. **错误分类**：业务码失败、HTTP 非 200、响应不是合法 JSON、必填参数缺失（不发请求）、
   上下文取消；
6. **配置默认值**：零值补齐、URL 与路径规整。

要求：

- 服务端在 handler 内按收到的键序重算签名并比对，等价于真实网关的校验方式；
- 测试不依赖外网，不依赖真实站点；
- 断言使用具体值，避免只判断 `err != nil`；
- 提交前 `go test ./...` 全绿，覆盖率以单包 90% 以上为目标（当前实现为 96% 量级）。

## 九、文档

### 9.1 保存路径

机器可读的规格与人读的说明分开放：规格进 `Meta/`，说明进 `Docs/`，两边目录层级一致、
文件名一致。文件与目录的命名规则见 [`FileNamingSpec.md`](FileNamingSpec.md)。

| 类型 | 路径 | 内容 |
| --- | --- | --- |
| OpenAPI 规格 | `Meta/OpenAPI/<厂商>/<接口组>/<接口名>.yaml` | 机器可读，供工具预览、生成与 lint |
| 接口说明 | `Docs/OpenAPI/<厂商>/<接口组>/<接口名>.md` | 面向人阅读的参数、签名、响应与示例 |
| 跨接口说明 | `Docs/OpenAPI/<厂商>/<接口组>/<主题>.md` | 不绑定单个接口的规则，如签名（`Signature.md`） |
| 目录索引 | `Docs/OpenAPI/<厂商>/<接口组>/README.md` | 文件清单、命名约定、与代码的对应关系 |

目录结构示例：

```
Meta/OpenAPI/MooMoo/QuoteAPIV2/
└── GetKLine.yaml

Docs/OpenAPI/MooMoo/QuoteAPIV2/
├── README.md
├── GetKLine.md
└── Signature.md
```

约定：

- `<厂商>` 用来源的稳定名称（如 `MooMoo`），`<接口组>` 用接口路径中的版本或系列名
  （如 `QuoteAPIV2`），不再拆更深的层级；
- `<接口名>` 与 Go 方法名、`operationId` 三者一致（如 `GetKLine`），`.yaml` 与 `.md` 同名；
- 新增接口必须同时提交 `.yaml` 与 `.md`，不能只提交其中一份；
- 跨接口的公共规则（签名、鉴权、公共响应结构）单独成文放 `Docs/` 侧，
  不要塞进某一个接口的规格里；同理，通用的 `components` 可以在各接口的 `yaml` 中
  各自定义，不跨目录共享文件；
- 两份文件分处不同目录，`md` 中引用规格要用能在仓库内跳转的相对路径，
  例如 `../../../../Meta/OpenAPI/MooMoo/QuoteAPIV2/GetKLine.yaml`；
- 规格不进 `Docs/`，说明不进 `Meta/`；两边都不放在 Go 包目录下，避免与代码混在一起。

### 9.2 规格内容（yaml）

- 使用 OpenAPI 3.0.3，一个接口一个文件；
- `operationId` 与 Go 方法名一致，查询参数的书写顺序与代码中的构造顺序一致；
- 响应统一用 `code` / `message` / `data` 描述，响应示例至少给成功一份；
- 可复用的结构放 `components.schemas`，`$ref` 不得悬空；
- `$ref` 旁不要放会被忽略的兄弟字段（`description`、`nullable` 等），
  需要补充说明时用 `allOf` 包裹；
- 字段类型混用时用 `oneOf` 或 `FlexNumber` 这类名字描述，并说明取值形态。

### 9.3 说明内容（md）

排版、标题、表格与链接的写法遵循 [`MarkdownSpec.md`](MarkdownSpec.md)；本节只约束接口说明
的内容顺序。

按固定小节组织，顺序如下：

1. **接口**：表格列出方法、站点、路径、`operationId`、代码入口、备注（如无分页、无时间范围、
   返回排序与过滤由调用方完成）；
2. **请求参数**：查询参数（表格，注明顺序即签名键序）、请求头、请求体
   （`GET` 无请求体也要显式写明）；
3. **签名规则**：算法细节统一写在 `Signature.md`，这里只描述与本次请求相关的签名输入
   与要点，并链接过去，避免两份文档各写一套算法；
4. **响应**：响应头、外层结构、字段表、示例；
5. **业务码**：列出 `0`、常见失败码及处理建议；
6. **相关实现**：指向对应的 `client.go`、`signature.go` 与测试文件。

字段表要求：

- 多类型不要挤在一个单元格里，拆成「字符串形式」「数值形式」等独立列，
  并在单元格里写具体写法与承载类型；
- 有精度含义的要写清楚：十六进制截断长度、浮点承载类型（如 `float64` 的 IEEE 754
  双精度、有效数字位数）、整数类型（如 `int64`）、小数位是否补零或四舍五入；
- 可缺失的字段在说明列注明可能为 `null`，不要只在类型里写。

### 9.4 一致性

- 站点行为变化时：先实测 → 更新 `yaml` → 更新 `md` → 修改实现；
- `yaml` 与 `md` 必须同步提交，不允许只改一边；
- 文档中引用的代码路径必须真实存在，不引用尚未创建的文档或文件。

## 十、提交前检查清单

```bash
gofmt -l .
go build ./...
go vet ./...
go test ./...
```

上述检查在 CI（`.github/workflows/CICD.yml`）中对 `main`、`dev` 的推送与 PR 各跑一遍，
提交前最好先在本地过一遍。

- [ ] 方法名能看出接口，且与 `operationId` 一致
- [ ] 请求参数有序构造，值已字符串化
- [ ] 响应解析保留原始精度，`null` 与零值可区分
- [ ] 错误可按类型与业务码判定，`Error()` 不丢原因
- [ ] 测试覆盖签名、装配、解析、错误分类，且不依赖外网
- [ ] `Meta/OpenAPI/` 下的规格与 `Docs/OpenAPI/` 下的说明同名成对，且与实现一致
- [ ] `md` 中的相对链接可跳转，引用的代码路径真实存在
- [ ] 字段表未把多类型挤在一格，精度与承载类型已写明
- [ ] CI 的格式检查、`go vet`、构建与 `go test` 均通过
