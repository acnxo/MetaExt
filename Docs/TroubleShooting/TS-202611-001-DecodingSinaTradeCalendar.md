# 新浪交易日历编码的逆向分析

## 一、概要

| 项 | 内容 |
| --- | --- |
| 问题 | `klc_td_sh.txt` 返回的字符串不是明文日期，需要还原算法才能得到交易日 |
| 结论 | 算法为「Base64 字符表 → 6 位位流 → 头部校验 + 起止游标 + 游程压缩」 |
| 验证 | 解码得 8796 个交易日，范围 1990-12-19 ~ 2026-12-31，逐年数量与 A 股吻合 |
| 落地 | `component/quote/sina/finance/cnatradecalendar`，纯标准库实现，覆盖率 100% |

本文记录从「只有一段无法阅读的字符串」到「可用 Go 复现的解码器」的完整过程，
包括走错的弯路，便于以后遇到同类加密资源时复用这套方法。

## 二、目标与约束

原始响应：

```text
var datelist="LC/AAApNDXCw6mHbaPgkryxXv10eAJP1LW0SD39aT7+NV44Xba3PxCgTdrp5BkYVAc11hWvg0c/...";var KLC_TD_SH=datelist;
```

约束：

- 只能从该 `txt` 资源解析，不允许换用其他数据源；
- 不能引入第三方依赖，只能用 Go 标准库实现；
- 必须能解释清楚每一步，不能「抄一段能跑的代码」了事；
- 解析失败要能明确报错，不能用空列表兜底。

## 三、排查过程

### 3.1 第一步：拿到真实样本

先抓一次响应并存盘，后续所有推导都基于同一份样本，避免样本漂移导致结论无法复现：

```bash
curl -sS --compressed 'https://finance.sina.com.cn/realstock/company/klc_td_sh.txt' \
  -H 'user-agent: Mozilla/5.0' -H 'referer: https://finance.sina.com.cn/'
```

关键观察：响应头 `content-type: text/plain`、`cache-control: max-age=120`、
`last-modified` 存在，说明这是站点定期生成的静态文件，而非实时接口。

### 3.2 假设一：这就是普通 Base64（失败）

提取引号内字符串，长度 469。标准 Base64 的长度必须是 4 的倍数，而 469 不是，
直接解码报错：

```text
Invalid base64-encoded string: number of data characters (469) cannot be
1 more than a multiple of 4
```

去掉首字符或末字符强行凑成 468 位再解码，得到的字节可打印率只有 40%~43%，
既不是 JSON 也不是日期文本，说明它不是「Base64 包了一层明文」。

### 3.3 假设二：Base64 后再做单字节 XOR 或加常数（失败）

如果只是简单异或，遍历 256 个 key 后应当出现大量 ASCII 数字（日期是 `19901219`
这类 8 位数字）。实际最佳结果只有 30 个数字字符（共 351 字节），远低于明文预期，
且分布随机。加常数同理。排除。

### 3.4 假设三：351 字节是「每天的位图」（失败，但排除方法值得记）

351 字节 = 2808 位。如果每一位代表一天，用「每 7 位为一周、交易日应占 5 位」
这个特征可以验证。于是统计每个 7 位窗口里 1 的个数分布：

| 假设 | 期望分布 | 实测 |
| --- | --- | --- |
| 位图 | 集中在 4~5 个 1 | 0~7 都有，4 或 5 仅占 48%，接近随机 |

结论：不是位图。这一步的价值在于——用**数据分布特征**排除假设，比逐个试错高效。

### 3.5 假设四：去站点前端脚本里找解密函数（失败）

思路是「谁在消费这个变量，谁就有解密代码」。抓取新浪行情页并检索 `KLC_TD`、
`klc_td`，页面里没有任何引用；再抓页面加载的两个行情 JS（`utils-hq.js`、
`stock20180116.js`），也没有。说明解密发生在别处或已下线，此路不通。

### 3.6 假设五：找公开实现（成功）

用 GitHub 代码搜索按字符串定位调用方，找到多个引用该资源的仓库：

| 仓库 | 做法 | 可用性 |
| --- | --- | --- |
| `akfamily/akshare` | `tool_trade_date_hist_sina` 把 `hk_js_decode` 作为 JS 源码交给 `py_mini_racer` 执行 | 不可直接阅读：本质是执行站点侧脚本，看不到算法 |
| `WackyGem/Fleur` | 文档 `docs/references/remote_endpoint/sina__calendar.md` 给出可读 Python 实现 | 可读，可逐行对照 |
| `yuancloud/jsshare` | 调用 `util.hk_js_decode(str)` 后拿到日期串 | 只能看到入口 |

所以「akshare 里的解密逻辑」本身并不是可直接阅读的算法，它是一段待执行的站点脚本。
真正可读的算法来自同一算法的 Python 移植版本，我按那份实现移植到 Go，再用真实样本验证。

**这一点必须写清楚**：本次不是「读了 akshare 源码就抄过来」，而是
「定位算法 → 找可读实现 → 自己移植 → 用真实数据验证」。

## 四、算法解析

### 4.1 位流

引号内每个字符按标准 Base64 字符表映射为 0~63 的 6 位值，**低位在前**拼成位流：

```text
字符 'L' → 11 → 001011（按位读顺序）
```

整个串就是一条连续的位流，后续所有字段都从这条位流里按位切出来。

### 4.2 头部与校验和

| 字段 | 位宽 | 说明 |
| --- | --- | --- |
| 保留字段 | 12 | 本样本为 139，含义未确认，不参与判断 |
| 校验字段 | 6 | 与 `63` 异或得到校验和，只接受 `0` 或 `1` |

本样本前 3 个字符是 `LC/`，第三个字符 `/` 对应 63，`63 ^ 63 = 0`，校验通过。
若数据损坏或格式变更，校验和会落到 `0/1` 之外，此时必须报错而不是继续解析。

### 4.3 起止游标

| 字段 | 位宽 | 本样本值 |
| --- | --- | --- |
| 起始游标 | 18 | 0（解析时减 1 作内部游标） |
| 结束游标 | 18 | 13161 |

游标不是日期，而是「天数序号」，需要经过 4.5 的换算才变成日期。

### 4.4 游程压缩

这是最难读的部分。日历并非逐日罗列，而是用「连续区间 + 变长编码」压缩：

1. 每到一个区间边界，先读 1 位标志；
2. 标志为 1 时，再读**变长符号位**，调整累计游程长度 `l`；
3. 按 `l × 3` 位读入本区间的重复天数（计数值减 1 后为实际重复次数）。

变长符号位的编码方式：

| 读到的位 | 含义 |
| --- | --- |
| 第 1 位 | 方向：`1` 正向、`0` 反向 |
| 后续连续的 `1` | 增量大小，遇到 `0` 结束 |

也就是说，`10` 表示 +1、`110` 表示 +2、`0` 表示 -1、`010` 表示 -2。
`l` 是**累计量**，可以为负；为负时该段长度为 0，不消耗位。

### 4.5 日期换算

```text
日期 = 1970-01-01 + (7657 + 游标) 天
```

游标每日加 1；若落在被折叠的周末位置则向前跳过，因此还原出的日期天然不含周末。

`7657` 这个常数是本算法的关键锚点：`1970-01-01 + 7657 天 = 1990-12-19`，
正好是**上交所开市日**。这个巧合本身就是正确性的强证据——如果是猜的算法，
不可能刚好落在这个日期上。

## 五、验证方法

只「能跑通」不足以证明算法正确，我用了四层验证：

| 层次 | 检验项 | 结果 |
| --- | --- | --- |
| 边界 | 首日、末日 | 1990-12-19、2026-12-31 |
| 总量 | 交易日数量 | 8796，与逐年累加一致 |
| 分布 | 每年交易日数 | 年均约 240 天，1991 年 255 天（早期周六开市），符合史实 |
| 语义 | 特定日期判定 | 国庆 `2026-10-01`、周末、`2027-01-01` 均为非交易日 |

另外用深市资源 `klc_td_sz.txt` 做了交叉验证：同一算法解出 8781 个交易日、
起点 1991-01-02，与深交所实际开市时间吻合。一个算法同时正确解出两个市场的日历，
基本可以排除「碰巧对上」的可能。

## 六、移植到 Go 时踩的三个坑

| 坑 | 现象 | 原因与修正 |
| --- | --- | --- |
| 符号位方向读反 | 总数 8874，节假日被当成交易日 | 首位为 `1` 是**正向**增量，我最初写成了负向 |
| 把负游程当错误 | 解析直接失败在第一个区间 | 负长度表示「本段 0 位」，不是异常，应记为 0 且不读位 |
| 样本手抄错误 | 总数 9360，且从第 407 个字符开始错位 | 把 `NjEn` 抄成了 `NjEN`；改为**用脚本从原始样本生成常量** |

第三个坑的教训最实用：**测试里的长常量不要手抄**。抄错一个字符，错误会伪装成
「算法有 bug」，排查成本极高。现在的做法是脚本生成、测试里再用长度与总量断言兜底。

排查这类「前 N 项一致、之后错位」的问题，有效手段是导出中间状态逐项对比：
把两边每次读游程时的 `(位置, 偏移, 读到的值)` 打成文本，`diff` 一次就能定位到
第一次分叉的位置，比盯着代码看快得多。

## 七、可复用的排查套路

面对「加密/编码的公开资源」，按这个顺序推进：

1. **先固化样本**：抓一次存盘，全流程用同一份数据，结论才可复现；
2. **量纲判断**：看长度是否能被 4/3/8 整除，先猜编码族（Base64、位图、定长记录）；
3. **用统计排除**：像 3.4 那样用「期望分布」快速否掉假设，比逐个试错省时间；
4. **找消费方**：谁在用这个变量，谁就有算法；页面脚本找不到就搜公开仓库；
5. **区分「可读实现」与「可执行代码」**：混淆 JS 只能跑不能读，要找人类写的移植版；
6. **找锚点日期**：算法里往往有基准常数，用「它算出来的首个日期是否等于真实开市日」
   来验证，比单纯「能解析」强得多；
7. **交叉验证**：同一算法套用到结构相似的另一份数据（如深市），结果也合理才算稳；
8. **落测试**：把真实样本内嵌进测试，断言总量与边界，格式变更时能立刻发现。

## 八、结论

- 该资源不是「加密」，而是**自定义位流 + 游程压缩**，没有密钥，算法公开可推导；
- 算法关键常数 `7657` 对应 1990-12-19，可作正确性锚点；
- 实现不依赖任何第三方库，测试内嵌真实样本、不依赖网络；
- 已知缺口：数据源本身缺 `1992-05-04`，实现不擅自补，文档如实标注。

相关实现：`component/quote/sina/finance/cnatradecalendar`；接口说明见
[GetTradeCalendar.md](../OpenAPI/Sina/Finance/CnaTradeCalendar/GetTradeCalendar.md)。
